今天早上只吃了一个前几天在盒马买的苹果，之后的大部分时间都花在云上历史 AKSK 的安全治理上。

从公有云责任共担模型来看，厂商负责“云本身的安全”，企业则要对自己放在云上的身份、配置和数据负责。AKSK 是云账号的持久化访问凭证，也应当成为企业自己守住的第一道边界。

很多初创企业刚上云时，第一目标都是让业务尽快跑起来，使用和配置上的不规范问题往往留到后面补。AKSK 也因此经常被随意保存、复制或共用。它的利用门槛很低，一旦泄露，却可能直接导致核心数据被读取、核心业务被中断，甚至让云账户失去控制。对依赖云运行的初创企业来说，AKSK 的安全确实是一条生命线。

这轮治理中，常见的 AKSK 使用问题大致有四类：

1. **AKSK 随意传播**：出现在办公软件、办公电脑、企业文档、项目代码、配置文件、主机或容器环境变量里。
2. **AKSK 权限过大**：初创企业往往业务优先，权限粒度较粗，可能直接授予整个 ECS、ACK、OSS 等服务的权限，甚至授予云账户管理员权限。
3. **AKSK 环境公用**：生产、测试和开发环境共用一个 AKSK，员工在办公网内就可能直接访问公司的核心敏感数据。
4. **AKSK 业务共用**：一个 AKSK 被多个业务部门同时使用，出了问题很难定位归属人和实际使用方。

以上这些问题，我在这轮治理里基本都遇到了。

从外部攻击视角看，云上 AKSK 的常见泄露面主要有三类：

1. 前端资源文件或后端接口响应里直接暴露 AKSK 明文。
2. 应用存在任意文件读取漏洞，攻击者可以获取环境变量；如果没有额外的密钥保护，AKSK 往往就在其中。
3. 利用 SSRF 漏洞，以应用服务器为跳板访问云上或企业内网资源。常见路径有两种：一种访问主机或集群的元数据服务，获取对应角色的 STS 临时凭证；另一种访问企业内部组件服务，例如未授权的 Nexus，拉取内部 Maven 组件包，再分析包内是否硬编码了明文 AKSK。AKSK 是长期凭证，STS 则是短期凭证，两者泄露后的风险周期并不相同。

AKSK 最终还是通过 IAM 账户和策略获得云服务权限。运维通常按照业务需求授权，但策略名称和实际展开后的权限往往存在差距。

我遇到过一个比较典型的场景：业务只是需要边缘云服务 A 的只读权限，审计后却发现该策略实际包含 SLS 日志服务的全量读取，个别情况下甚至包含 OSS 对象存储的全量读取。因此，不能只看策略名称或授权意图，还要展开策略中的 Action、Resource 和条件，再结合 AKSK 的实际使用链路判断风险。

云上服务很多，哪些权限真正有风险，也很难靠简单的规则覆盖。要深挖某个 IAM 身份的风险，安全工程师需要理解具体云服务的业务语义，而不只是认识几个权限名称。

我的实践是先梳理云服务提供的 API，再围绕 API 建立风险模型。以 IAM 为例，创建访问密钥、绑定策略、访问目标资源，就可以构成一条完整的风险链。沿着 API 反推可执行动作和资源范围，才能更准确地判断一个 AKSK 能走到哪里。过去人工梳理 API、IAM Action 和资源范围之间的映射非常繁琐，现在借助 AI 可以大幅提高效率，但结论仍然需要用云服务文档和实际策略核对。

历史存量 AKSK 的治理也不是一次扫描或一次性轮换就能完成的。它涉及凭证归属、使用链路、替换成本和业务连续性。安全工程师可以推动治理，但企业也需要 KMS 等安全基础设施，减少密钥的明文流转和保存。帮助大家把钥匙放到更安全的地方，往往比反复提醒“不要泄露”更有效。
