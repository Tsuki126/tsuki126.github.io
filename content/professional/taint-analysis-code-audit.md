## 在追什么

污点分析要回答一个问题：**外部可控的输入，有没有可能不做净化就到达危险操作**。

三个概念：source（输入点，比如 HTTP 参数、请求头）、sink（危险操作，比如拼接 SQL、执行命令、反序列化）、propagation（从 source 到 sink 之间的传递规则）。

## 为什么在框架代码上失效

真实项目里，输入几乎不会从 controller 直接流到 sink，中间要经过 DTO、service、DAO，还有一堆注解和反射。静态分析看不到运行时的动态绑定，于是链路断开，漏报就出现了。

这也是为什么纯工具的审计报告需要人过一遍：**工具报的是"数据流可达"，审计员判断的是"攻击者能不能真的构造出来"**。

## 一个实用的判断顺序

1. 这个 sink 是不是真的危险（有没有参数化、有没有白名单）。
2. 链路中间有没有净化函数，净化是否彻底。
3. 攻击者到达 source 需不需要认证。

按这个顺序看，能过滤掉大部分"工具说严重、实际不可利用"的条目。

## 结论

污点分析是审计的起点而不是终点。它的价值在于把可疑路径收窄到几十条，剩下的判断只能靠人。
